# Формат исполняемых файлов .box

## Назначение и область действия

`.box` — собственный формат программ BoxOS: контейнер именованных частей.
Машинный код, данные, точки входа, описание входных данных, настройки,
сведения о сборке и диагностические имена представлены отдельными частями.
Содержимое можно исследовать без запуска программы.

Документ описывает версию `BOX_VERSION = 1` по текущим определениям
`src/include/box_format.h`, общему читателю `box_reader.h`, писателю
`box_pen.h`, упаковщику `tools/pack.c` и загрузчику ядра `box_load.c`.
Проверка исходников выполнена 2026-11-13, HEAD `bb6f5ac4`.
Бинарные правила формата и ограничения текущей реализации различаются
и ниже описаны отдельно.

Текущая исполняемая платформа — x86-64. В заголовке `.box` нет отдельного
поля архитектуры, ABI, разрядности, порядка байтов или алгоритма хеширования.
Нельзя считать его универсальным контейнером машинного кода разных платформ.

Расширение имени не определяет содержимое. Загрузчик распознаёт файл по
начальным байтам. На томе тег `app` или `utility` обозначает запускаемую
программу; эти теги относятся к файлу TagFS и не являются полями `.box`.

## Основные свойства

- **Именованные части.** Вид части определяется ключом её имени, например
  `code`, `form` или `about:ru`; номера `BoxKind` в файл не записываются.
- **Каноническая раскладка.** Таблица, имена и содержимое идут в одном порядке,
  смещения однозначно определяются размерами и выравниванием.
- **Расширение через новые имена.** Неизвестные необязательные части можно
  пропустить; обязательная неизвестная часть запрещает запуск.
- **Два уровня целостности.** Печать SHA-256 защищает описание контейнера,
  а каждая часть имеет собственный SHA-256.
- **Выборочное чтение.** Для получения одной части не нужно читать весь
  файл. Загрузчик читает необходимые для запуска части и проверяет их хеши.
- **Размещение без динамической линковки.** Часть `fixups` позволяет ядру
  выбрать базу образа и прибавить её к заранее определённым словам.
- **Права памяти по назначению.** `code` получает R+X, `const` — R,
  `data` — R+W; исполняемые страницы не становятся записываемыми для процесса.
- **Метаданные в памяти.** Заданные части можно заранее загрузить для
  чтения программой; ядро создаёт таблицу их адресов и имён.
- **Самоописание программы.** Form описывает вход и результат, Settings —
  доступные настройки, Life — способ жизни, Recipe — происхождение сборки,
  Nameplate — имена функций для диагностики.
- **Общие правила для всех потребителей.** Ядро, BoxLib и инструменты
  основной системы используют один исходник читателя.

Целостность не означает авторство: текущая реализация не проверяет
цифровую подпись и не устанавливает доверие к издателю программы.

## Порядок байтов и единицы

Все целые числа записываются в little-endian. `u16`, `u32` и `u64` ниже
означают беззнаковые числа размером 2, 4 и 8 байт. Смещения и размеры
измеряются в байтах, если явно не указано другое.

Бинарная раскладка задаётся смещениями, а не выравниванием структур
компилятора. Читатель использует `BoxU16()`, `BoxU32()`, `BoxU64()`;
писатель — `BoxPut16()`, `BoxPut32()`, `BoxPut64()`.

Имена частей и дверей записываются без завершающего NUL. Для них всегда
передаётся длина. Строки Nameplate, напротив, завершаются NUL.

## Общая раскладка файла

```text
0
┌──────────────────────────────────────┐
│ Заголовок: HeaderSize байт            │
├──────────────────────────────────────┤ ← TableAt = HeaderSize
│ PartCount записей по 80 байт          │
├──────────────────────────────────────┤ ← NamesAt
│ Имена частей подряд, без NUL          │
├──────────────────────────────────────┤ ← PrefixBytes
│ Нулевые байты выравнивания            │
├──────────────────────────────────────┤ ← Offset первой части
│ Содержимое первой части              │
├──────────────────────────────────────┤
│ Выравнивание и следующие части        │
└──────────────────────────────────────┘ ← FileSize
```

Обязательные соотношения:

```text
TableAt     = HeaderSize
NamesAt     = TableAt + PartCount × 80
PrefixBytes = NamesAt + NamesSize
Offset[i]   = AlignUp(EndOfPrevious, Alignment[i])
End[i]      = Offset[i] + Size[i]
FileSize    = End[PartCount - 1]
```

Для первой части `EndOfPrevious = PrefixBytes`. Для `code`, `const` и
`data` выравнивание равно `4096`, для остальных частей — `8`.
Выравнивание выбирается по ключу имени даже для неизвестной версии части.

Произвольные промежутки, лишние байты после последней части и отдельная
таблица свободного пространства не предусмотрены. Промежутки выравнивания
должны содержать нули. У пустой части `Size = 0`, но её выровненное
смещение всё равно участвует в раскладке: перед пустой последней частью
могут находиться нулевые байты выравнивания.

## Заголовок

Текущий писатель создаёт заголовок размером `80` байт.

| Смещение | Размер | Тип | Поле | Значение и назначение |
|---|---|---|---|---|
| `0x00` | 8 | `u8[8]` | Magic | `89 42 4F 58 0D 0A 1A 0A`. |
| `0x08` | 2 | `u16` | Version | Версия контейнера, сейчас `1`. |
| `0x0A` | 2 | `u16` | HeaderSize | Размер заголовка, сейчас писатель выдаёт `80`. |
| `0x0C` | 4 | `u32` | PartCount | Число записей таблицы; ноль запрещён. |
| `0x10` | 8 | `u64` | TableAt | Смещение таблицы, равно `HeaderSize`. |
| `0x18` | 8 | `u64` | NamesAt | Смещение общего массива имён. |
| `0x20` | 8 | `u64` | NamesSize | Размер общего массива имён. |
| `0x28` | 8 | `u64` | FileSize | Полная длина файла; должна совпадать с фактической. |
| `0x30` | 32 | `u8[32]` | Seal | Печать SHA-256 описания контейнера. |

Magic содержит видимое `BOX`, старший бит и последовательности переводов
строки. Это позволяет распознать формат и заметить некоторые повреждения
при передаче бинарного файла через текстовый канал.

Читатель версии 1 принимает `HeaderSize >= 80`, кратный `8`. Неизвестные
байты расширенного заголовка входят в печать, но текущий читатель их не
интерпретирует. Он не требует, чтобы они были нулевыми. Это не разрешение
использовать неизвестную версию контейнера: `Version != 1` отвергается.

В заголовке нет адреса запуска: он находится в двери `start` части `doors`.
Нет также даты сборки, имени программы, размеров стека и списка импортов.
Часть этих сведений выражается метаданными, остальное отсутствует.

## Запись таблицы частей

Каждая запись занимает `80` байт. Смещения в этой таблице относительны
началу записи, а не началу файла.

| Смещение | Размер | Тип | Поле | Назначение |
|---|---|---|---|---|
| `0x00` | 8 | `u64` | Offset | Начало содержимого в файле. |
| `0x08` | 8 | `u64` | Size | Число байт содержимого в файле. |
| `0x10` | 8 | `u64` | Memory | Логический размер части в памяти. |
| `0x18` | 8 | `u64` | Place | Смещение загружаемой части от базы образа. |
| `0x20` | 4 | `u32` | Flags | Маска флагов. |
| `0x24` | 2 | `u16` | Version | Версия внутреннего формата части. |
| `0x26` | 2 | `u16` | NameLength | Длина имени в байтах. |
| `0x28` | 4 | `u32` | NameAt | Смещение имени от `NamesAt`. |
| `0x2C` | 4 | `u32` | Reserved | Обязательно `0`. |
| `0x30` | 32 | `u8[32]` | Hash | SHA-256 ровно `Size` байт части. |

`Offset` и `Place` относятся к разным пространствам: первый — к файлу,
второй — к образу в памяти. Обычный адрес загружаемой части равен
`ImageBase + Place`. Положение части в файле не определяет её адрес.

Для известных частей версии 1:

- у `data` допустимо `Memory >= Size`; недостающий хвост заполняется нулями;
- у остальных известных частей требуется `Memory == Size`;
- у `code`, `const`, `data` поле `Place` кратно `4096`;
- у остальных известных частей `Place = 0`;
- `code.Size` должен быть больше нуля;
- конец загружаемой части не должен выходить за `BOX_PLACE_LIMIT`;
- округлённые до страниц диапазоны `code`, `const`, `data` не пересекаются.

`BOX_PLACE_LIMIT = 0x0000800000000000`, то есть граница в 128 ТиБ от базы
в модели читателя. Реально доступная область образа в ядре значительно
меньше и проверяется отдельно.

Размеры неизвестной необязательной части не получают правил конкретного
вида. При этом общие проверки её имени, флагов, положения в файле и
границ продолжают действовать. `LOAD_AT_START` дополнительно требует
`Memory == Size` и `Place == 0` независимо от известности вида.

## Имена и порядок частей

Имя имеет форму тега: `key` или `key:value`.

Правила `BoxNameSpelled()`:

- ключ непустой и занимает не более `255` байт;
- если есть первый `:`, значение непустое и занимает не более `255` байт;
- дальнейшие двоеточия допустимы внутри значения;
- запрещены байты `0x00..0x20`, `0x7F`, запятая и последовательность `...`;
- завершающего NUL нет; пробелы также запрещены;
- регистр значим, сравнение побайтовое;
- отдельной проверки корректности UTF-8 нет.

Максимальная допустимая длина составного имени — `511` байт: ключ,
двоеточие, значение. Поле длины шире этого ограничения.

Записи строго отсортированы по `BoxNameOrder()`:

1. Сравниваются ключи побайтово; более короткий общий префикс идёт первым.
2. Для одинакового ключа простое имя идёт перед именами со значением.
3. Значения сравниваются побайтово тем же способом.

Например: `about`, `about:en`, `about:ru`, `code`, `icon:128`, `icon:64`.
Числа в значениях не преобразуются в числа: `128` идёт перед `64`.
Повтор одинакового полного имени запрещён.

Имена лежат подряд в порядке таблицы. `NameAt` первой записи равен нулю,
каждой следующей — сумме предыдущих длин. Все `NamesSize` байт должны
быть использованы именами; скрытые строки и пробелы между ними запрещены.
Поиск части по полному имени выполняется двоичным поиском.

Среди стандартных видов значение после `:` разрешено только для `about`,
`form`, `settings`, `icon`. Например, `code:avx2` и `needs:cpu` недопустимы.
Для собственных неизвестных ключей разрешены обе формы имени.

Часть `form:ru` не подменяет часть `form`: системный поиск вида через
`BoxPartOfKind()` использует простое имя. Для конкретного варианта нужен
поиск полного имени через `BoxPartFind()`.

## Флаги

| Бит | Значение | Имя | Действие |
|---|---|---|---|
| 0 | `0x01` | `BOX_FLAG_MUST_UNDERSTAND` | Отказать, если вид или его версия неизвестны читателю. |
| 1 | `0x02` | `BOX_FLAG_LOAD_AT_START` | Загрузить содержимое на отдельные страницы только для чтения и включить в таблицу частей процесса. |
| 2 | `0x04` | `BOX_FLAG_COMPRESSED` | Пометить содержимое как сжатое. Декодер и общий формат сжатия сейчас не реализованы. |

Любой бит вне `0x07` отвергается. Флаги не задают произвольные права
страниц и не содержат разрешений доступа к службам системы.

У присутствующих `code`, `const`, `data`, `fixups`, `doors`, `thread`,
`needs` обязателен `MUST_UNDERSTAND`. Это требование понимания части,
а не требование наличия всех перечисленных частей в каждом файле.
Безусловно нужны только известные простые `code` и `doors`; внутри
`doors` обязательно наличие `start`.

Для `code`, `const`, `data`, `fixups`, `doors`, `thread`, `needs`, `hints`
запрещены `LOAD_AT_START` и `COMPRESSED`. Первые три загружаются как образ,
остальные используются по собственному назначению. У `names` запрещён
`LOAD_AT_START`: её загрузка выполняется отдельно самим ядром.

Комбинация `LOAD_AT_START | COMPRESSED` запрещена для любой части.
Загружаемая по флагу часть может быть неизвестной: ядро переносит её
байты без интерпретации, с правами R и NX, выбирая адрес самостоятельно.

Наличие `COMPRESSED` в общей маске не означает готовую поддержку сжатия.
`program_part_read()` возвращает `-ERR_UNSUPPORTED` для такой части.
Текущий загрузчик не выполняет распаковку; не используйте этот флаг для
метаданных, которые системный потребитель читает как обычные байты.
Для неизвестных необязательных данных флаг позволяет обозначить состояние,
но способ их декодирования должен определять отдельный согласованный формат.

## Версии и расширение

Контейнер и каждая часть имеют отдельную версию. Сейчас стандартные
части читаются при `Version = BOX_PART_VERSION = 1`.

| Ситуация | Результат текущего читателя |
|---|---|
| Неизвестная версия контейнера | Отказ всего файла. |
| Неизвестное имя без `MUST_UNDERSTAND` | Часть сохраняется в таблице, её содержимое можно пропустить. |
| Неизвестное имя с `MUST_UNDERSTAND` | `BOX_PART_UNKNOWN_REQUIRED`. |
| Известное имя с неизвестной версией и `MUST_UNDERSTAND` | `BOX_PART_VERSION_REQUIRED`. |
| Известное имя с неизвестной версией без обязательного флага | Для интерпретации часть считается неизвестной. |
| Неизвестный бит флагов | Отказ независимо от необязательности части. |

Новая версия необязательной части не гарантирует сохранение всех функций
программы на старой системе. Например, неподдерживаемая версия настроек
может быть пропущена. Если программа без части работать не может,
писатель должен явно обозначить это обязательным флагом.

## Каталог стандартных частей

| Имя | Назначение | Текущее использование |
|---|---|---|
| `code` | Машинный код | Обязательная область R+X. |
| `const` | Константы | Необязательная область R, NX. |
| `data` | Изменяемые данные и нулевой хвост | Необязательная область R+W, NX. |
| `fixups` | Места прибавления базы | Размещение образа по выбранной ядром базе. |
| `doors` | Именованные входы | Обязательная дверь `start`. |
| `thread` | Шаблон TLS | Создание локальных данных потоков. |
| `names` | Nameplate версии 1 | Диагностические имена функций. |
| `signature` | Подпись автора | Имя зарезервировано; проверка подписи не реализована. |
| `needs` | Требования к процессору | Проверка CPUID и включённого состояния регистров. |
| `hints` | Ожидаемые ресурсы | Подготовка стека, сообщение об ожидаемой памяти. |
| `life` | Способ жизни программы | `task`, `stays`, `serves`, `rise`. |
| `form` | Вход и результат программы | Чтение оболочкой и программой. |
| `settings` | Декларация настроек | Типы, значения по умолчанию и дерево настроек. |
| `recipe` | Происхождение сборки | Инструмент, Use Context, исходные файлы и их хеши. |
| `about` | Описание для человека | Известное имя; отдельной обязательной схемы содержимого здесь нет. |
| `icon` | Значок `icon:N` | Известное имя; бинарная схема пикселей текущим форматом не определена. |
| `works` | Описание обрабатываемых файлов | Известное имя; автоматический подбор приложений этим кодом не реализован. |
| `asks` | Запрашиваемые возможности и объяснение | Известное имя; механизма выдачи разрешений из этой части нет. |

Каталог имени не равнозначен наличию обработчика его содержимого.
Стандартный читатель проверяет общие поля перечисленных видов, но не
превращает `signature`, `icon`, `works` или `asks` в работающую службу.
Сам флаг `MUST_UNDERSTAND` проверяет известность имени и версии на уровне
общего читателя; он не добавляет отсутствующую предметную реализацию.
В частности, известное имя `signature` не включает проверку подписи.

## Код, константы и данные

### `code`

Непустой массив машинного кода. `Memory == Size`. Виртуальное начало —
`ImageBase + Place`. Страницы доступны процессу для чтения и исполнения,
запись запрещена. Все двери должны попадать в файловые байты этой части,
а не в дополнение страницы.

### `const`

Данные только для чтения, `Memory == Size`, исполнение запрещено.
Загрузчик не выделяет им права записи даже на время применения `fixups`:
он изменяет ещё не опубликованные физические страницы через ядро.

### `data`

Изменяемые данные. Первые `Size` байт читаются из файла, диапазон
`[Size, Memory)` заполняется нулями. Например, `Size = 24`, `Memory = 4096`
означает 24 байта начальных данных и 4072 нулевых байта.

Часть с `Size = 0` может описывать полностью нулевую область данных.
Хеш считается от файлового содержимого, для пустого содержимого — SHA-256
пустой последовательности. Дополнительные байты нулевого хвоста в хеш
не передаются, но его размер входит в таблицу, защищённую печатью.

Таблица допускает не более одной части каждого из этих трёх видов:
полные имена уникальны, а суффиксы у них запрещены. В ней нет отдельной
части `.bss`: её роль выполняет разность `Memory - Size` у `data`.

## Двери: doors

`doors` содержит именованные точки входа. Дверь `start` обязательна;
именно её выбирает текущий загрузчик для запуска. Дополнительные двери
разрешены структурой, но это не механизм динамического экспорта функций.
Текущий `pack` создаёт одну дверь `start` из `e_entry` исходного ELF.

Заголовок части:

| Смещение | Тип | Назначение |
|---|---|---|
| `0` | `u32` | Число дверей `Count`. |
| `4` | `u32` | Ноль. |

Далее следуют `Count` записей по 16 байт:

| Смещение в записи | Тип | Назначение |
|---|---|---|
| `0` | `u64` | Смещение точки входа от базы образа. |
| `8` | `u32` | Смещение имени от начала массива имён дверей. |
| `12` | `u16` | Длина имени. |
| `14` | `u16` | Ноль. |

Массив имён начинается на `8 + Count × 16`, занимает весь оставшийся
хвост части и не содержит NUL. Имена подчиняются `BoxNameSpelled()`,
отсортированы по `BoxNameOrder()`, не повторяются и лежат подряд.

Для каждой двери требуется:

```text
code.Place <= DoorOffset < code.Place + code.Size
EntryAddress = ImageBase + DoorOffset
```

Одна дверь `start` занимает `8 + 16 + 5 = 29` байт.
Смещение двери не является ни смещением от начала `code`, ни файловым
смещением: оно измеряется от базы всего образа.

## Перенос образа: fixups

`fixups` — последовательность `u64` без собственного заголовка.
Она кодирует смещения 8-байтовых слов образа, к которым нужно прибавить
выбранную базу. Кодирование соответствует относительным перемещениям RELR.

Наличие известной части `fixups`, даже пустой, означает для загрузчика,
что образ допускает выбор базы. Отсутствие части означает фиксированное
размещение с `ImageBase = 0`: значения `Place` уже являются адресами.

### Прямые записи и битовые карты

Если младший бит слова равен нулю, всё слово — прямое смещение `P`.
В список перемещений включается `P`, а начало следующего окна становится
`P + 8`.

Если младший бит равен единице, остальные 63 бита — карта относительно
начала текущего окна. Бит `k`, где `1 <= k <= 63`, обозначает слово
`Window + (k - 1) × 8`. Затем окно сдвигается на `63 × 8 = 504` байта.
Несколько карт могут следовать подряд.

Например, слова `[0x1000, 0x0B]` обозначают смещения
`0x1000`, `0x1008`, `0x1018`: у `0x0B` установлены биты 0, 1 и 3,
где бит 0 служит признаком карты.

Проверки:

- размер части кратен 8;
- первое непустое слово — прямое смещение;
- полученные смещения строго возрастают, повторения запрещены;
- каждое смещение кратно 8 и меньше `BOX_PLACE_LIMIT`;
- все 8 байт изменяемого слова лежат в файловом содержимом одной из
  `code`, `const`, `data`;
- перемещение в нулевой хвост `data` или за границу части запрещено.

Читатель принимает допустимую последовательность прямых записей и карт;
писатель уплотняет соседние места в карты. Поэтому единая раскладка
контейнера не означает, что произвольные логически эквивалентные
последовательности RELR побайтово одинаковы.

### Применение

Загрузчик выполняет `Word = Word + ImageBase` в подготовленных физических
страницах до их отображения процессу. Отдельной таблицы добавляемых
значений нет: исходное значение уже записано в самом слове образа.

Это не разрешение внешних символов. Здесь нет таблицы импортов,
`DT_NEEDED`, PLT-поиска или загрузки разделяемых библиотек.

## Локальные данные потоков: thread

`thread` задаёт шаблон TLS, а не готовый поток и не его стек.

| Смещение | Размер | Тип | Поле |
|---|---|---|---|
| `0` | 8 | `u64` | `Align`: выравнивание TLS. |
| `8` | 8 | `u64` | `InitBytes`: размер начального содержимого. |
| `16` | 8 | `u64` | `TotalBytes`: начальное содержимое вместе с нулевым хвостом. |
| `24` | 8 | `u64` | Ноль. |
| `32` | `InitBytes` | байты | Начальный шаблон. |

`Align` должен быть ненулевой степенью двойки, не больше `4096`.
`InitBytes == Part.Size - 32`, `TotalBytes >= InitBytes`,
`TotalBytes <= BOX_PLACE_LIMIT`. Заголовок таблицы самой части сохраняет
`Memory == Size`: объём создаваемого TLS задаёт внутренний `TotalBytes`.

Для главного Strand ядро создаёт нулевые страницы, копирует начальный
шаблон и размещает после выровненного TLS блок TCB из двух `u64`.
Первое слово TCB содержит его собственный адрес, второе равно нулю;
полученный указатель используется для TLS через FS.

Текущая реализация дополнительных Strand допускает TLS, чей выровненный
размер не превышает одной страницы: `ImageThreadFitsStrand()`.
Главный поток может иметь больший TLS при наличии места в образе.
Это ограничение реализации потоков, а не 32-байтового заголовка формата.

Шаблон копируется как есть. `pack` отвергает перемещения, попадающие в
инициализируемую часть TLS: базу нельзя применить только к исходной копии,
а затем безусловно переносить адреса в шаблоны новых потоков.

## Имена функций: names

Содержимое `names` — Nameplate версии 1 из
`src/include/nameplate_format.h`. Заголовок занимает 32 байта:

| Смещение | Тип | Поле |
|---|---|---|
| `0` | `u32` | `Magic = NAMEPLATE_MAGIC = 0x4E504C54`. |
| `4` | `u32` | `Version = 1`. |
| `8` | `u32` | `EntryCount`. |
| `12` | `u32` | `NameBytes`. |
| `16` | `u64` | `BaseAddress`: адрес, относительно которого заданы смещения функций. |
| `24` | `u64` | `TotalBytes`: полный размер Nameplate. |

После заголовка идут три параллельных массива по `EntryCount` элементов
`u32`: `Offset`, `Size`, `NameOffset`. Затем следуют `NameBytes` байт
NUL-завершённых имён.

```text
OffsetsAt     = 32
SizesAt       = 32 + 4 × EntryCount
NameOffsetsAt = 32 + 8 × EntryCount
NamesAt       = 32 + 12 × EntryCount
TotalBytes    = 32 + 12 × EntryCount + NameBytes
FunctionStart = ImageBase + BaseAddress + Offset[i]
```

Смещения функций строго возрастают; `Size = 0` означает неизвестную
длину. Имена C++ хранятся в исходном кодировании символов линкера,
без обязательного деманглирования. Три массива позволяют двоичному
поиску обращаться только к массиву адресов.

Проверка заголовка требует `1 <= EntryCount <= 2^24`,
`NameBytes >= EntryCount`, согласованного `TotalBytes` и его размещения
в доступных байтах. Она не является полным сканированием всех имён:
поиск проверяет границы используемых индексов отдельно.

Ядро размещает `names` после основных областей образа на страницах R, NX.
Хеш содержимого проверяется; корректность заголовка определяет, будет ли
Nameplate зарегистрирована для диагностики. Непригодный заголовок имён
не равнозначен отказу всего контейнера на уровне `BoxRead()`.

Практическое свойство: имена доступны в памяти при аварии, без обращения
к файловой системе и без полной ELF-таблицы символов. Это не замена всем
отладочным данным DWARF: строки исходников и локальные переменные такой
таблицей не описываются.

## Общие правила текстовых частей

Общая оболочка читается `BoxTextBegin()`:

- строки разделяются LF (`0x0A`), последняя может не иметь LF;
- запрещены байты ниже `0x20`, кроме LF, и байт `0x7F`;
- NUL, TAB и CR запрещены; окончания CRLF не подходят;
- разделитель слов — обычный пробел;
- пустые строки и строки только из пробелов пропускаются общим читателем;
- первая непустая строка содержит два слова: имя вида и `1`;
- для `about:ru` общая версия заголовка, если она используется, относится
  к виду `about`, а не к полному имени варианта;
- байты выше `0x7F` не проверяются на корректность UTF-8.

Общий читатель не определяет грамматику всех текстовых частей. У Form,
Recipe и Settings есть собственные потребители; они могут требовать
более строгий заголовок или структуру. Например, `form_parse()` и
`recipe_parse()` ожидают свою строку версии в начале текста.

Неизвестные строки обычно пропускаются ради расширения, но ошибка в
известном поле не должна рассматриваться как произвольный комментарий.
Поддержка комментариев зависит от конкретной грамматики.

## Требования к процессору: needs

Пример:

```text
needs 1
cpu avx2
cpu bmi2
```

Каждая известная строка `cpu` должна состоять ровно из двух слов.
Текущий загрузчик проверяет наличие CPUID-листа, указанный бит
возможности и необходимое включённое состояние сохранения регистров.
Неизвестное имя возможности после `cpu` вызывает отказ, как и отсутствие
требуемой возможности. Неизвестный первый вид факта пропускается.

Поддерживаемые имена:

| CPUID: лист, подлист, регистр | Имена и номера битов |
|---|---|
| `0x1, 0, ECX` | `sse3:0`, `pclmul:1`, `ssse3:9`, `fma:12`, `cx16:13`, `sse4.1:19`, `sse4.2:20`, `movbe:22`, `popcnt:23`, `aes:25`, `avx:28`, `f16c:29`, `rdrand:30`. |
| `0x7, 0, EBX` | `bmi1:3`, `avx2:5`, `bmi2:8`, `avx512f:16`, `avx512dq:17`, `rdseed:18`, `adx:19`, `avx512cd:28`, `sha:29`, `avx512bw:30`, `avx512vl:31`. |
| `0x80000001, 0, ECX` | `lzcnt:5`. |

`fma`, `avx`, `f16c`, `avx2` дополнительно требуют маску состояния
`0x06`; перечисленные возможности AVX-512 — `0xE6`. Проверяется маска
`g_xsave_mask`, которой система располагает для сохранения состояния.
Наличие инструкции у процессора без нужного состояния ОС недостаточно.

Декларация не анализирует машинный код. Текущий `pack` не выводит `needs`
автоматически из флагов компилятора и не переносит произвольную секцию
`.boxos.needs`: его список извлекаемых метаданных задан явно.

## Подготовка ресурсов: hints

```text
hints 1
stack 512 KiB
memory 16 MiB
```

Поддерживаются строки `stack NUMBER UNIT` и `memory NUMBER UNIT`.
Число — десятичное без знака и ведущих нулей, кроме самого `0`.
Единицы регистрозависимы: `B`, `KiB`, `MiB`, `GiB`.
Переполнение `u64`, неизвестная единица, лишнее слово или повтор
одного известного указания вызывают отказ. Незнакомые виды указаний
пропускаются.

`stack` задаёт желаемый резерв главного стека. Значение округляется
вверх до страницы и ограничивается диапазоном
`CONFIG_USER_STACK_RESERVE_MIN..CONFIG_USER_STACK_RESERVE_MAX`.
При ограничении ядро сообщает, что именно предоставлено. Это не обещание
физически выделить весь резерв сразу и не снятие системного лимита.

`memory` сравнивается с `CABIN_HEAP_MAX_SIZE`: превышение сообщается
в журнале, но само по себе не меняет лимит и не создаёт отдельную квоту.
Без `hints` используется штатный резерв стека из конфигурации ядра.

## Способ жизни: life

```text
life 1
serves
rise
```

Допустимо не более одного слова из `task`, `stays`, `serves` и не более
одного `rise`; каждое известное слово занимает собственную строку.
Без части или без слова способа жизни используется `task`, без `rise`
автоматический подъём не запрашивается.

| Слово | Смысл |
|---|---|
| `task` | Программа выполняет работу и заканчивается; запускающий ожидает завершения. |
| `stays` | Программа остаётся работать самостоятельно, ожидание завершения не требуется. |
| `serves` | Долгоживущая программа, обслуживающая других. |
| `rise` | Запрос системного повторного запуска после аварии в поддерживаемом сценарии. |

Оболочка читает способ жизни. Загрузчик ядра сохраняет из этой части
признак `rise`. Читатель пропускает неизвестные слова для совместимости,
а текущий упаковщик отвергает их при сборке, чтобы не записывать
объявление, которое никто не выполнит.

`rise` не означает перезапуск любой программы после любого завершения.
Текущий механизм следит за системным автозапуском и его повторными
подъёмами, требует сохранения у файла тегов программы и `autostart`,
не поднимает выброшенный в корзину файл. Авария и переполнение стека
могут инициировать подъём; обычный выход и принудительное завершение — нет.
Программы, запущенные человеком, система таким способом не поднимает.

Пауза начинается с 1 секунды и растёт до 16 секунд; работа в течение
минуты сбрасывает последовательность. Три последовательные аварии,
каждая в первые 10 секунд после запуска, прекращают подъёмы.
Это политика `rise.h`, а не поля бинарного заголовка `.box`.

В C/C++ декларация создаётся `BOX_LIFE("serves\nrise")` из `box/life.h`.

## Вход и результат: form

```text
form
takes things Sources "the files to read"
takes optional text Note "a note for the result"
gives things
```

Общая форма поля:

```text
takes [optional] KIND [NAME] "описание"
gives things
gives text
```

| KIND | Значение |
|---|---|
| `thing` | Один файл. |
| `things` | Один или несколько файлов. |
| `name` | Одно слово имени, существующего или нового. |
| `words` | Список слов. |
| `text` | Оставшийся текст команды как текстовое поле. |
| `into` | Имя назначения после `->`, которым распоряжается программа. |

Без `optional` поле обязательное. Необязательное имя поля начинается
латинской буквой, затем допускает буквы, цифры и `_`; оно уникально среди
полей и не равно `them`, `it`, `all`, `everywhere`. Текущий предел —
`BOX_FORM_FIELDS = 16`. Потребитель Form ограничивает её текст 65536 байтами;
это лимит BoxLib, а не максимальный размер произвольной части `.box`.

Form описывает контракт, а не заполненные значения запуска. Заполненные
поля передаются отдельно через Luggage. `gives things` объявляет возврат
идентификаторов файлов через Souvenir; сами файлы и Souvenir в образ не
записываются. `gives text` описывает текстовый результат.

В C/C++ `BOX_FORM(Text)` из `box/form.h` создаёт `.boxos.form` и добавляет
заголовок `form` самостоятельно. `BOX_FORM("")` допустим и означает отсутствие
входных полей. Упаковщик удаляет завершающие NUL секции и переносит текст
в часть `form` с `LOAD_AT_START`.

`pack` проверяет общую текстовую оболочку Form, но не выполняет полный
разбор `takes` и `gives`. Успешная упаковка поэтому не доказывает,
что оболочка сможет заполнить все объявленные поля.

Подготовка запуска, работа с полями в C++ и запись в Luggage описаны
отдельно в [руководстве Form](boxcxx/form.md). Передача идентификаторов
результата — в [руководстве Souvenir](boxcxx/souvenir.md).

## Настройки: settings

Часть содержит декларацию доступных настроек и их значений по умолчанию.
Пользовательские изменения хранятся отдельно на томе; редактирование
настроек не требует изменения исполняемого файла и его печати.

```text
settings 1
greeting on-or-off default on "show a greeting"
cursor "cursor appearance"
    shape one-of block underline bar off default underline "shape"
    blink number from 100 to 5000 ms or off default off "blink interval"
    color color default #AAAAAA "color"
history on-or-off default on next-start "keep history"
```

Формы строки:

```text
NAME "описание группы"
NAME KIND [параметры типа] default VALUE [next-start] "описание"
```

Отступ образует дерево: соседние элементы имеют одинаковый отступ,
дочерние — больший. Группа без собственного значения должна содержать
хотя бы один элемент; элемент со значением тоже может иметь потомков.
Текущий предел глубины — `SETTINGS_DEPTH_MAX = 8`.

Имя: строчная латинская буква, затем строчные буквы, цифры и `-`;
конечный `-` запрещён, длина не более `32`, зарезервированы `settings`
и `default`. Имена уникальны среди соседей одного родителя.

| KIND | Допустимое значение |
|---|---|
| `on-or-off` | `on` или `off`. |
| `number from A to B [UNIT] [or off]` | Целое в диапазоне `A..B`; границы представлены `int64_t`. `or off` разрешает `off` как ноль и требует положительной нижней границы. |
| `word` | Одно непустое слово без пробелов и двойной кавычки. |
| `text` | Текст одной строки, включая пустой. |
| `one-of W1 W2 ...` | Одно из двух или более различных допустимых слов. |
| `color` | Имя цвета из `SettingColorNames()` или `#RRGGBB`. |
| `key` | Поддерживаемое сочетание с `ctrl` или `alt`, разбираемое `key_chord.h`. |

Значение может быть словом или текстом в двойных кавычках. Кавычки нужны
для пустого текста, пробелов по краям и буквального значения `default`.
`next-start` обозначает применение при следующем запуске; без него
декларация допускает применение во время работы. Реакцию программы на
изменение обеспечивает библиотека и код приложения, не загрузчик образа.

Доступные имена цветов: `black`, `dark-gray`, `gray`, `light-gray`,
`white`, `red`, `green`, `blue`, `cyan`, `yellow`, `amber`, `orange`,
`purple`, `pink`, `brown`. Не следует автоматически приравнивать этот
список к набору `painter::core::Colors`.

Строка, начинающаяся после пробелов с `#`, является комментарием.
Содержимое `.box` подчиняется общему запрету TAB и CR независимо от
вспомогательных функций подсчёта отступов в читателе настроек.

Текущий `pack` проверяет каждую декларацию `SettingsDeclaredNext()`
и отвергает ошибки. Во время чтения программа может пропустить
неподдерживаемую настройку вместе с её потомками и сохранить остальные.
В C/C++ декларацию создаёт `BOX_SETTINGS` из `box/settings.h`; в `.box`
она переносится как `settings` с `LOAD_AT_START`.

## Происхождение сборки: recipe

Часть связывает программу с файлами, прочитанными при её создании.
Ниже `HEX` означает ровно 64 строчные шестнадцатеричные цифры SHA-256;
это обозначение поля, а не допустимое буквальное содержимое строки.

```text
recipe 1
by assemble
context demo
from #41 HEX planets.asm
from #42 HEX planets.inc
```

- `by` встречается один раз и содержит непустое имя инструмента.
- `context` встречается один раз; пустое значение означает отсутствие
  Use Context при сборке.
- Нужна хотя бы одна строка `from`; первая обозначает исходный файл,
  с которого началась сборка.
- Идентификатор после `#` — ненулевой `u64` в десятичной форме без
  ведущих нулей.
- После хеша через пробел следует имя файла, занимающее остаток строки.
- Писатель заменяет управляющие байты в отображаемом имени на `?`.
- Незнакомые виды строк пропускаются; неверная известная строка отвергается.

Идентификатор используется для обращения к файлу, имя — для объяснения
человеку. Сравнение текущих байтов с сохранённым хешем позволяет различить
неизменившийся, изменившийся и отсутствующий либо выброшенный файл.
Политика проверки находится в `recipe_check()`, а не в загрузчике `.box`.

Recipe не включает исходные файлы внутрь контейнера и не доказывает
воспроизводимость результата компилятора. Она фиксирует прочитанные входы.
Нативный сборщик может использовать её для повторной сборки в прежнем
контексте. Отсутствие Recipe допустимо, в том числе у программ,
собранных инструментами основной системы.

`pack` переносит `.boxos.recipe` в `recipe`, удаляя завершающие NUL;
проверяет текстовую оболочку, но не весь смысл `by`, `context`, `from`.

## Описание, значки, подбор файлов и запросы возможностей

### `about` и `about:язык`

Предназначены для сведений о программе для человека. Суффикс позволяет
нести несколько вариантов, например `about:ru` и `about:en`.
Текущие определения контейнера не задают обязательных полей описания
и механизма выбора языка. Нельзя обещать автоматическое отображение
такой части оболочкой только по наличию её имени.

### `icon` и `icon:N`

Суффикс задуман как размер квадратного значка, например `icon:64`.
Общий читатель проверяет его как обычное значение тега: он не требует
десятичного числа, не проверяет размер картинки и не определяет формат
пикселей, сжатие, альфа-канал или цветовое пространство.
PNG, RGBA и иные представления не следует считать установленной схемой
`icon` версии 1 без отдельного определения.

### `works`

Имя предназначено для описания файлов, с которыми работает программа,
через их теги. В рассмотренных определениях нет законченной грамматики
этой части и обработчика автоматического выбора программы по ней.

### `asks`

Имя предназначено для описания запрашиваемых возможностей и причины
запроса. В текущем контейнере оно не предоставляет полномочий и не
создаёт диалог выдачи разрешений. Политика доступа не выводится
из наличия текста `asks`.

### `signature`

Имя зарезервировано для подписи автора, связанной с печатью контейнера.
Текущий код не определяет завершённую бинарную схему подписи, алгоритм,
размещение ключа, правила доверия или исключения из вычисления печати.
Проверки подписи в загрузчике нет.

Общий алгоритм хеширования включает хеш любой части, в том числе части
с именем `signature`, в печать таблицы. Поэтому проектировать протокол
подписи простым добавлением «подписать Seal и положить подпись в часть»
без определения покрываемых данных нельзя: текущие правила сами такой
протокол не устанавливают.

## Целостность и печать

### Хеш части

Для каждой записи:

```text
Part.Hash = SHA256(File[Part.Offset : Part.Offset + Part.Size])
```

Хеш относится к исходным файловым байтам до применения перемещений,
не к содержимому памяти уже работающего процесса. При `COMPRESSED`
общая формула также относится к сохранённым байтам, не к результату
гипотетической распаковки.

### Печать контейнера

Печать считается по префиксу до конца имён с занулённым собственным
полем `[48, 80)`:

```text
Seal = SHA256(
    File[0:48]
    || ZeroBytes[32]
    || File[80:PrefixBytes]
)
```

Таким образом защищаются заголовок, таблица, имена и ожидаемые хеши
содержимого. Изменение байта части обнаруживается при её хешировании;
попытка изменить ожидаемый хеш изменяет печать.

Нулевые промежутки после имён не включены в печать и не принадлежат
хешам частей. Их значение задано правилом канонической раскладки и
проверяется отдельно через `BoxGapsZero()` или аналогичный проход.
Повреждение одного промежутка само по себе не меняет вычисляемую печать.

### Что именно подтверждает проверка

Корректная печать подтверждает согласованность описания, но без чтения
части не подтверждает её фактические байты. Для полной проверки файла
нужны печать, хеши всех частей и нулевые промежутки.

SHA-256 не содержит секретного ключа. Тот, кто может заменить весь файл,
может пересчитать и хеши, и печать. Эти проверки обнаруживают повреждения
и несогласованность, но не устанавливают автора или безопасность кода.

Изменение одной части требует обновления её хеша и печати. Если меняется
длина, также пересчитываются следующие смещения, имена и полная длина.
Обычный писатель сначала сортирует части, измеряет результат, затем
формирует весь контейнер и перечитывает его общим читателем.

## Как ядро загружает .box

1. Источник образа читается по смещениям. Начальные байты выбирают
   `BoxLoad()`; выбор не основывается на расширении имени.
2. Читаются первые 80 байт и проверяется заголовок.
3. Читается префикс до конца имён. Проверяются таблица, порядок,
   диапазоны, версии, обязательные части и печать.
4. При наличии читаются и проверяются по хешу `needs`, `hints`, `life`.
   Затем разбираются двери, TLS и перемещения.
5. Планируются основные области, Nameplate, переносимые метаданные,
   таблица загруженных частей и TLS главного Strand.
6. При наличии `fixups` ядро выбирает базу с ASLR; иначе использует нулевую
   базу и фиксированные адреса `Place`.
7. `code`, `const`, `data` и `names` читаются по страницам прямо в будущие
   физические страницы процесса; SHA-256 считается по мере чтения.
8. Применяются перемещения. Затем страницы отображаются с окончательными
   правами; страницы данных и TLS имеют NX.
9. Каждая часть с `LOAD_AT_START` читается, проверяется и размещается на
   отдельных страницах R, NX. Формируется таблица адресов частей.
10. Создаётся TLS и выбирается адрес `ImageBase + start`.

Загрузчик не обязан читать и хешировать `about`, `icon`, `recipe` или
другую часть, не нужную для запуска и не помеченную для загрузки.
Он также не вызывает полный `BoxGapsZero()`: все промежутки проверяются
при полном исследовании файла инструментом `inside`.

Чтение по страницам не означает demand paging. К моменту запуска
необходимые области уже прочитаны и проверены; файл не подгружается
по первому обращению процессора к каждой странице кода.

Текущая область образа ограничена
`[CABIN_CODE_START_ADDR, CABIN_CODE_END_ADDR)`, сейчас это
`[0xC000, 0x10000000)`. В неё должны поместиться не только основные части,
но и Nameplate, загруженные метаданные, их таблица и TLS.
Это отдельное ограничение от `BOX_PLACE_LIMIT` общего читателя.

Для ошибок структуры загрузчик сейчас возвращает `ERR_INVALID_ELF`,
хотя распознанный формат — `.box`; подробная причина выводится через
`BoxVerdictText()` с именем проблемной части. Ошибки памяти, чтения,
размера образа и отображения могут иметь собственные коды.

## Таблица частей в памяти программы

Ядро создаёт таблицу из `src/include/box_loaded.h` и передаёт адрес
через `CabinInfo.parts_addr`. Это другая структура, не копия файлового
заголовка или таблицы `.box`.

Заголовок `BoxLoadedHead`, 40 байт:

| Смещение | Тип | Поле |
|---|---|---|
| `0` | `u32` | `Count`: число представленных в памяти частей. |
| `4` | `u32` | `Bytes`: полный размер таблицы с именами. |
| `8` | `u8[32]` | `Seal`: печать файла, из которого запущена программа. |

За ним идут `Count` записей `BoxLoadedPart` по 24 байта:

| Смещение в записи | Тип | Поле |
|---|---|---|
| `0` | `u64` | `Address`: фактический виртуальный адрес содержимого. |
| `8` | `u64` | `Size`: логический размер в памяти; для `data` включает нулевой хвост. |
| `16` | `u32` | `NameAt`: смещение имени от начала всей таблицы. |
| `20` | `u16` | `NameLength`: число байт имени. |
| `22` | `u16` | `Version`: версия части. |

После записей расположены имена без NUL, в исходном порядке таблицы
контейнера. Записи существуют для загруженных `code`, `const`, `data`,
`names` и частей с `LOAD_AT_START`. Временные `doors`, `fixups`, `thread`
не становятся записями только потому, что загрузчик читал их при запуске.

Таблица отображается только для чтения. Она позволяет находить части
без знания выбранной базы или внутренних адресов загрузчика.
`program_part_loaded()` возвращает указатель в уже существующую память,
а не выделяет копию. Срок жизни указателя — время жизни процесса;
права содержимого определяются частью: `data` остаётся изменяемой.

Для остальных частей используется `CabinInfo.program_file` и
`program_part_read()`: префикс проверяется по печати, нужная часть —
по хешу, результат возвращается отдельной копией с дополнительным NUL
вне её логического размера. Ограничение размера задаёт вызывающий код.

Печать в памяти фиксирует, из какого описания был запущен процесс.
Само наличие этого поля не выполняет автоматическую проверку, что
позже изменённый файл на томе остаётся той же версией программы:
потребитель, которому это важно, должен сравнивать идентичность отдельно.

## Получение .box из ELF

Обычная сборка C/C++ сначала создаёт ELF для инструментов основной
системы, затем `build/pack` преобразует его в `.box`.
ELF с отладочными данными остаётся доступен разработчику.

Команда после сборки упаковщика:

```sh
build/pack src/userspace/utils/timezone.elf /tmp/timezone.box
```

Аргументы: входной ELF и путь выходного `.box`. Код завершения `0`
означает успех, `1` — отказ чтения, преобразования или записи,
`2` — неверное число аргументов. Упаковщик также проверяет свой SHA-256
на известном векторе; вспомогательная ошибка памяти хеширования может
завершить инструмент с кодом `2`.

### Преобразование областей

| ELF | Часть .box | Преобразование |
|---|---|---|
| `PT_LOAD`, исполняемый | `code` | Выравнивание начала вниз до страницы, начальный промежуток заполняется нулями. |
| `PT_LOAD`, только чтение | `const` | Аналогичное выравнивание; отдельно переносимые метаданные исключаются из хвоста. |
| `PT_LOAD`, записываемый | `data` | Файловое содержимое и отдельный нулевой хвост в `Memory`. |
| `PT_LOAD` без R/W/X | Не переносится | Служебные таблицы линкера не становятся областью программы. |
| `e_entry` | `doors` | Одна дверь `start`. |
| `PT_TLS` с ненулевым объёмом памяти | `thread` | Выравнивание, начальные байты и полный размер TLS. |
| `SHT_RELA`, `SHT_RELR` статического PIE | `fixups` | Относительные перемещения в кодировании RELR. |
| `.nameplate` | `names` | Отдельная диагностическая таблица. |
| `.boxos.form` | `form` | Текст без конечных NUL, `LOAD_AT_START`. |
| `.boxos.settings` | `settings` | Текст без конечных NUL, `LOAD_AT_START`, полная проверка деклараций. |
| `.boxos.life` | `life` | Текст без конечных NUL, проверка всех слов. |
| `.boxos.recipe` | `recipe` | Текст без конечных NUL. |

`ET_EXEC` сохраняет фиксированные адреса, части `fixups` у него нет.
`ET_DYN` используется как статический PIE; упаковщик добавляет `fixups`
даже при отсутствии перемещений. Штатная схема линковки PIE задаёт
адреса относительно нулевой базы.

Для RELA допускается только `R_X86_64_RELATIVE` без символа. Добавляемое
значение из записи предварительно записывается в целевое слово,
чтобы загрузчику `.box` оставалось только прибавить базу.
Адреса из RELA и RELR объединяются, сортируются и проверяются на повторения.

`code` и `const` получают в файле также те нули исходного сегмента,
которые у ELF существовали только в памяти; только `data` может иметь
`Memory > Size`. Упаковщик допускает по одной области каждого вида
и отвергает одновременно записываемую и исполняемую область.

Из хвоста констант исключаются `.nameplate`, `.boxos.form`,
`.boxos.settings`, `.boxos.life`. Если после начала этих метаданных
находятся обычные константы, упаковщик отказывает: штатный linker script
размещает переносимые метаданные последними. Recipe также извлекается
в отдельную часть, но не входит в список `CarriedApart()` для обрезки
хвоста констант; её удаление из любой произвольной области ELF обещать нельзя.

### Что упаковщик отвергает

- Файл, не являющийся ELF64 little-endian для x86-64.
- Тип ELF, отличный от `ET_EXEC` или `ET_DYN`, например объектный `ET_REL`.
- Запрос интерпретатора `PT_INTERP` или разделяемой библиотеки `DT_NEEDED`.
- Область с W+X, несколько областей одного назначаемого вида,
  некорректные диапазоны и отсутствующий код.
- Перемещения `SHT_REL`, неизвестные виды RELA, повторные места,
  перемещения вне файловых байт образа или в шаблоне TLS.
- Перемещения в ELF, объявленном фиксированным `ET_EXEC`.
- Неверную общую текстовую оболочку переносимых метаданных,
  ошибочные настройки и неизвестные либо противоречивые слова Life.
- Результат, не проходящий общий читатель `.box` и специальные читатели
  дверей, TLS и перемещений.

Произвольные ELF-секции не превращаются автоматически в части `.box`.
Для собственных частей нужен писатель контейнера или расширение
согласованного процесса сборки.

### Включение в образ BoxOS

Корневой `Makefile` перечисляет программы в `VOLUME_CONTENT` как `.elf`,
но `Box()` преобразует их пути в `build/box/<имя>.box`. Правила `BoxRule`
вызывают упаковщик, и на том попадает `.box` с назначенными тегами.
Например, команда `timezone` соответствует файлу `timezone.box`.

Полный путь первой программы на C++ описан в
[руководстве](boxcxx/first-program.md).

## Нативное создание внутри BoxOS

BoxASM создаёт контейнер напрямую через
`src/userspace/utils/assemble/boxasm_link_box.c` и тот же `box_pen.h`.
Промежуточный ELF для такого пути не является обязательным этапом.
Нативный сборщик формирует код, данные, двери, перемещения, TLS,
Nameplate, Form, Settings, Life и Recipe из своих входов.

Писатель предоставляет:

| Интерфейс | Назначение |
|---|---|
| `BoxPenMeasure()` | Отсортировать описания частей на месте и измерить размер контейнера. |
| `BoxPenWrite()` | Записать в буфер нужного размера таблицу, имена, байты, хеши и печать; перечитать результат. |
| `BoxPenDoors()` | Отсортировать и сформировать часть дверей. |
| `BoxPenThread()` | Сформировать заголовок и начальные байты TLS. |
| `BoxPenFixups()` | Закодировать возрастающий список мест в прямые слова и карты RELR. |

Общий писатель не выделяет память: буферы и SHA-256 предоставляет
вызывающая сторона. Сортировка изменяет массив описаний; хранящиеся
в нём указатели на имена и содержимое должны оставаться действительными
во время записи. Для дверей, TLS и перемещений вызов с нулевым выходным
буфером используется для измерения, следующий вызов — для записи.

`BoxPenWrite()` проверяет заголовок, таблицу, промежутки, печать,
структуры `doors`, `thread`, `fixups`. Он не заменяет все предметные
проверки Form, Settings, Recipe, Needs или Hints: их выполняют
соответствующие писатели и потребители.

## Пример расчёта раскладки

Рассмотрим структурный контейнер из трёх частей:

- `code`: один байт `C3`, `Place = 0`, `Memory = 1`;
- `doors`: одна дверь `start` со смещением `0`, размер 29 байт;
- `fixups`: пустая последовательность, размер 0;
- у всех `Version = 1`, `MUST_UNDERSTAND`.

Байт `C3` приведён для проверки структуры, а не как полноценный код
завершения процесса BoxOS. Валидатор контейнера не доказывает
содержательную корректность машинных инструкций.

Имена занимают `4 + 5 + 6 = 15` байт: `codedoorsfixups`.

| Элемент | Смещение | Размер |
|---|---|---|
| Заголовок | `0` | `80` |
| Таблица | `80` | `240` |
| Имена | `320` | `15` |
| Префикс целиком | `0` | `335` |
| Нулевой промежуток | `335` | `3761` |
| `code` | `4096` | `1` |
| Нулевой промежуток | `4097` | `7` |
| `doors` | `4104` | `29` |
| Нулевой промежуток | `4133` | `3` |
| Пустая `fixups`, конец файла | `4136` | `0` |

`FileSize = 4136`, `NamesAt = 320`, `NamesSize = 15`.
В таблице имён `NameAt` равны `0`, `4`, `9`.
У первой и третьей частей соответственно `Size = 1` и `Size = 0`,
но обе записи имеют полноценные SHA-256. Печать покрывает первые
335 байт с занулённым собственным полем.

## Порядок проверки собственного читателя

Используйте общий читатель вместо ручного разбора непроверенных смещений:

1. `BoxReadHead()` на первых 80 байтах и независимо известной длине файла.
2. Получение `Head.PrefixBytes` байт, затем `BoxRead()`.
3. `BoxSealHolds()` с реализацией SHA-256.
4. `BoxPartAt()`, `BoxPartFind()` или `BoxPartOfKind()` для выбора части.
5. Чтение её диапазона и `BoxPartHolds()`.
6. Специальный разбор содержимого, если потребитель использует его смысл.
7. Для полного исследования файла — все хеши и `BoxGapsZero()`.

`BoxRead()` проверяет раскладку, а не выполняет все последующие шаги.
`BoxPartAt()` и итератор перемещений рассчитаны на уже проверенные
структуры. Нельзя использовать их как независимый валидатор произвольного
фрагмента памяти.

Читатель не выделяет память и не хранит глобальное состояние. Представления
`BoxTable`, `BoxPart`, `BoxDoors`, `BoxThread` содержат указатели в исходные
буферы; буферы должны оставаться доступными и неизменными всё время
использования представлений. `BoxHasher` хранит пользовательский контекст;
параллельные вычисления требуют отдельных контекстов либо синхронизации.

## Причины отказа общего читателя

Символические значения находятся в `BoxVerdict`. Это коды интерфейса
читателя, а не поля исполняемого файла.

| Код | Причина |
|---|---|
| `BOX_OK` | Нарушение не найдено выполненным этапом проверки. |
| `BOX_NOT_BOX` | Начальные байты не совпали с Magic. |
| `BOX_TRUNCATED` | Не хватает заявленных заголовком байтов. |
| `BOX_VERSION_UNKNOWN` | Неизвестная версия контейнера. |
| `BOX_HEADER_SIZE` | Недопустимый размер заголовка. |
| `BOX_NO_PARTS` | Нулевое число частей. |
| `BOX_TABLE_MISPLACED` | Таблица начинается не после заголовка. |
| `BOX_NAMES_MISPLACED` | Имена начинаются не после таблицы. |
| `BOX_FILE_SIZE` | Заявленная длина не совпала с фактической. |
| `BOX_ENTRY_NOT_ZERO` | Ненулевое резервное поле записи. |
| `BOX_FLAGS_UNKNOWN` | Неизвестный бит флагов. |
| `BOX_NAME_MISPLACED` | Неверное положение или длина имени. |
| `BOX_NAME_SPELLING` | Имя не соответствует форме тега. |
| `BOX_NAME_ORDER` | Имена не отсортированы строго или повторяются. |
| `BOX_NAME_NOT_STANDARD` | Значение после `:` запрещено для данного вида. |
| `BOX_NAMES_LEFT_OVER` | Остались байты имён, не принадлежащие записям. |
| `BOX_PART_MISPLACED` | Содержимое не на первом допустимом выровненном смещении. |
| `BOX_PART_OUTSIDE` | Часть выходит за файл или не помещается её выравнивание. |
| `BOX_FILE_LEFT_OVER` | Файл продолжается после конца последней части. |
| `BOX_PART_MEMORY` | Размеры в файле и памяти не соответствуют правилам вида. |
| `BOX_PART_PLACE` | Недопустимое положение в образе. |
| `BOX_PART_FLAGS` | Флаги противоречат назначению части. |
| `BOX_PART_UNKNOWN_REQUIRED` | Неизвестная обязательная часть. |
| `BOX_PART_VERSION_REQUIRED` | Неизвестная версия обязательной части. |
| `BOX_LOADABLE_OVERLAP` | Загружаемые области разделяют страницу. |
| `BOX_NO_CODE` | Нет поддерживаемой части `code`. |
| `BOX_NO_DOORS` | Нет поддерживаемой части `doors`. |
| `BOX_SEAL` | Печать не совпала. |
| `BOX_PART_HASH` | Хеш содержимого части не совпал. |
| `BOX_GAP_NOT_ZERO` | Ненулевые байты выравнивания. |
| `BOX_DOORS_LAYOUT` | Некорректная структура дверей. |
| `BOX_DOOR_OUTSIDE_CODE` | Дверь указывает за файловые байты кода. |
| `BOX_NO_START` | Нет двери `start`. |
| `BOX_THREAD_LAYOUT` | Некорректный шаблон TLS. |
| `BOX_FIXUPS_LAYOUT` | Неверный размер или начало последовательности перемещений. |
| `BOX_FIXUP_ORDER` | Декодированные места перемещений не возрастают. |
| `BOX_FIXUP_OUTSIDE` | Перемещение не обозначает целое допустимое слово образа. |
| `BOX_TEXT_LAYOUT` | Некорректная общая текстовая структура. |

`BoxTable.Refused` и поля `RefusedName` указывают связанную с отказом
часть, если она уже определена. `BOX_NO_PART = 0xFFFFFFFF` обозначает
отсутствие такого индекса. Проверка останавливается на первом нарушении;
один файл может содержать и другие ошибки, до которых разбор не дошёл.

## Исследование и проверка инструментами

На основной системе после сборки:

```sh
tools/inside build/box/timezone.box
```

В BoxOS:

```text
inside timezone.box
```

Обе команды используют общий `inside_show.c`: показывают состав,
размеры, флаги, понятное содержимое известных частей, результат проверки
хешей, печати и промежутков. Наличие текста в выводе не запускает программу.

Коды завершения инструмента основной системы:

| Код | Значение |
|---|---|
| `0` | Исследованные файлы — целые контейнеры по выполненным проверкам. |
| `1` | Найдена повреждённая или некорректная `.box`. |
| `2` | Файл не является `.box`, в том числе когда это корректный ELF. |
| `3` | Файл не удалось прочитать либо не хватило ресурсов для проверки. |

При нескольких аргументах возвращается худший результат. Структурная
корректность `inside` не обещает доступности CPU, достаточного объёма
памяти и успешного поведения программы на конкретной машине.

Стенды запускаются из корня репозитория:

```sh
bash tools/box_stand.sh
bash tools/pack_stand.sh
bash tools/inside_stand.sh
```

`box_stand` собирает общий код в окружениях ядра, BoxLib и основной
системы, проверяет корректные контейнеры и точные причины отказа
повреждённых. `pack_stand` сравнивает упакованные программы с исходными
ELF и проверяет обязательные отказы. `inside_stand` проверяет вывод
и результаты исследователя, включая повреждённые файлы. Стенды основной
системы используют AddressSanitizer и UndefinedBehaviorSanitizer.

Эти стенды не заменяют загрузку ядром и исполнение на реальном оборудовании.
