    Всем привет,

    Я продолжаю работу над повышением функциональности своей ОС на реальном оборудовании. Сейчас я работаю над драйвером xHCI, а именно над его обеспечением работы на реальном оборудовании.

    У меня возникли некоторые проблемы с xHCI на ноутбуке:

    * Существует два xHC, из которых (пока) я выбираю тот, который используется для USB 2.0, потому что настройка обоих означает, что один и тот же физический порт будет генерировать события для обоих xHC, с чем я сейчас не хочу иметь дело.
    * Функция настройки порта корневого концентратора, работающая под QEMU, не выдает адрес устройству, при этом командное кольцо сообщает об ошибке TRB с кодом завершения 4 (сбой USB-транзакции) при попытке выдать TRB адреса устройства с BSR=0.

    Процесс инициализации моего порта выглядит следующим образом:

    1. Я обнаруживаю, что к порту подключено устройство, поскольку CCS=1 и CSC=1 для PORTSC.
    2. Я выполняю перезагрузку этого порта, поскольку это порт USB 2.0, и согласно спецификации, он будет оставаться в отключенном состоянии до тех пор, пока не будет выполнена перезагрузка, после чего он перейдет в включенное состояние (и устройство перейдет из состояния «Включено» в состояние «По умолчанию»).
    3. Выполните команду Enable Slot TRB с соответствующим типом слота и настройте контекст устройства в DCBAA.
    4. Выдайте TRB для адресного устройства с BSR=1 и настройте контекст ввода в соответствии со спецификацией (заблокируйте SET_ADDRESS, но позвольте xHC выполнить свои внутренние действия).
    5. Считайте дескриптор устройства из его конечной точки управления по умолчанию (это необходимо для устройств с высокой скоростью передачи данных, чтобы определить их максимальный размер пакета).
    6. Сбросить кольцо конечной точки управления по умолчанию в исходное состояние, чтобы снова получить DCS=1 и новый указатель извлечения из очереди.
    7. Наконец, я отправляю команду Address Device, на этот раз с BSR=0 и соответствующим максимальным размером пакета для EP0, чтобы xHC отправил пакет SET_ADDRESS.

    В QEMU всё работает отлично, устройство инициализируется и передаётся универсальному драйверу стека USB. Но на реальном оборудовании я постоянно получаю код завершения "ошибка транзакции USB" (4) на шаге 5 или шаге 7, если шаги 5-6 пропущены и максимальный размер пакета считается равным 8.

    I know QEMU is quite forgiving in terms of configuration, but I've spent quite a lot of time this week going through the spec's device init process to find what I might be missing, and can't find anything.

                I don't think an OS ever should change BARs, only read their settings.

                Also, I note that newer motherboards will no longer set the bus master and memory access bits, and if you fail to do that in the driver code, then the BARs will not work and always return FF when read. This is probably a protection means so non-activated PCI functions should not be able to access PCI, but it really doesn't work for malious hardware since it doesn't stop direct access to PCI from the hardware.

                  I do set bus mastering + MMIO, I also clear port IO enable and IRQ disable bits in the PCI configuration space's command register in my probe() function:

                  Code: Select all

                      let mut cmd = PciCommandRegister::from_bits_retain(info.config_space.command());
    cmd &= !(PciCommandRegister::DISABLE_INTERRUPTS | PciCommandRegister::ENABLE_IO);
    cmd |= PciCommandRegister::ENABLE_MEMORY | PciCommandRegister::BUS_MASTER;
    info.config_space.set_command(cmd.bits());
                  Also, an OS can update BARs if it wants to. I believe Linux remaps some BARs even in x86(-64). And on platforms like arm/riscv, you basically need to do that, because there might be no proper firmware to setup the BARs for you.

                              And here's what happens on my laptop (obviously, no handy xhci regs tracing) when an USB flash drive is plugged into an USB3.1 port:

                              Code: Select all

                              IRQ started 0x18

port 6 connected = true
Event Ring: port 6 changed

IRQ finished
IRQ started 0x18
Event Ring: port 2 changed

IRQ finished
##### I disconnect the flash drive
IRQ started 0x18
Event Ring: port 2 changed
port 2 connected = false
IRQ finished
                              So looks like when a USB flash drive is connected to an USB3.1 port, the xHC first sends two events (connect+disconnect) immediately regarding the USB3.1 (6) port, then it sends an event regarding USB2.0 port (2). Both are the same physical port.
                              After that, I never receive any events from the 6th port again.

                              I've also noticed that unlike QEMU, a real xHC also sets the PCD=1 in USBSTS when issuing interrupts, which means "any port has a change bit transition from 0 to 1". Not quite sure if that's relevant here.
